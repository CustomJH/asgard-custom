# Asgard Planning

기획은 문서 묶음이 아니라 하나의 추적 가능한 결정 흐름이다. 같은 계획 모델에서 필요한
뷰를 꺼낸다. AI는 구조화하고 누락을 찾지만 승인권자가 아니다.

## 응답 머리말

매 응답을 아래 네 줄 이내의 상태로 시작한다.

- `단계` — 현재 단계와 전체 순서
- `확정` — 이번 대화에서 승인된 결정
- `공백` — 다음 진행을 실제로 막는 항목
- `다음` — 지금 답할 한 질문 또는 수행할 한 행동

저장소, 연결된 문서, 프로젝트 메모리로 답할 수 있는 질문은 먼저 조사한다. 사용자 질문은
한 번에 하나만 하고 추천 기본값과 가장 큰 trade-off를 함께 준다. 답이 없어도 안전하게
진행할 수 있으면 `가정`으로 표시하고 계속한다.

## 계획 모델

각 항목에 안정적인 짧은 ID를 붙이고 다음 관계를 유지한다.

`근거 → 문제/기회 → 목표 → 요구사항 → 기능/정책 → 화면/흐름 → 수용 기준 → 구현 단위`

정본 저장 항목은 `id`, `kind`, `state`, `title`, `links`를 가진다. `links`는 위 관계의 다른
항목 ID만 가리킨다. 근거 항목에는 `source`와 `observed_at`을 추가해 출처와 관찰 시점을
잃지 않는다.

항목 상태는 다섯 가지뿐이다.

- `evidence` — 출처와 관찰 시점이 있는 사실
- `assumption` — 검증 전 가정
- `proposal` — AI 또는 팀의 제안
- `decision` — 승인권자가 확정한 선택
- `open` — 미해결 질문, 위험 또는 의존성

같은 사실을 여러 산출물에 복제하지 않는다. PRD, 기능명세, 구조도, 플로우, 로드맵은 이
모델의 뷰다. 변경 시 연결된 하위 항목과 충돌을 함께 보여 준다.

## 순차 흐름

이미 확인된 단계는 재질문하지 말고 통과한다. 각 단계의 출구 조건을 만족하기 전에는 다음
단계를 확정본처럼 말하지 않는다.

### 1. 시작점

입력은 세 갈래다.

1. 한 줄 아이디어 — 짧은 구조화 인터뷰로 시작
2. 기존 자료 — 회의록, 제안서, 리서치, 이슈, 로그에서 근거와 가정을 분리
3. 빈 계획 — 사용자가 직접 구조를 만들고 AI는 누락만 제안

확인할 것: 계획 대상, 승인권자, 기대 산출물, 제약, 이번 범위. 출구는 “무엇을 왜
계획하는지”를 한 문장으로 말할 수 있는 상태다.

### 2. 문제와 근거

현재 행동, 불편, 영향받는 사용자, 발생 맥락, 기존 대안, 관찰 근거를 연결한다. 사용자 발언과
해석을 분리하고, 출처 없는 시장 사실이나 수치를 만들지 않는다. 경쟁·시장·최신 관행이 실제
결정에 영향을 줄 때만 외부 조사를 한다.

출구: 핵심 문제/기회 하나, 근거 목록, 반증 가능 조건, 남은 가정.

### 3. 목표와 성공 조건

사용자 결과와 사업 결과를 분리한다. 성공 지표에는 정의, 단위, 기간, 분모, 데이터 원천,
기준값과 목표값의 출처를 기록한다. 수치가 없으면 `확인 필요`로 두고 측정 계획만 만든다.
비목표와 가드레일도 함께 확정한다.

출구: 목표, 비목표, 측정 계획, 실패·중단 조건.

### 4. 사용자와 맥락

실제 역할, 권한, 숙련도, 환경, 접근성 요구, 개인정보 경계를 정의한다. 근거 없는 페르소나
서사를 만들지 말고 “역할 + 상황 + 해야 할 일 + 제약”으로 최소화한다.

출구: 주요 행위자, 핵심 시나리오, 권한/제약 표.

### 5. 범위와 우선순위

기능보다 먼저 해결할 사용자 행동과 정책을 나눈다. `must / later / out`의 세 묶음으로
기본 범위를 잡는다. RICE, WSJF 같은 점수는 모든 입력값에 출처가 있을 때만 쓴다. 그렇지
않으면 영향, 위험, 학습 가치, 의존성으로 정성 순서를 만들고 이유를 적는다.

출구: 최소 검증 범위, 제외 범위, 우선순위 이유, 의존성.

### 6. 요구사항 구조

요구사항을 결과 중심으로 쓰고 기능, 정책, 비기능 요구사항으로 분해한다. 각 요구사항에는
근거/결정 ID, 소유자, 상태, 수용 기준을 연결한다. 애매한 형용사 대신 관찰 가능한 조건을
쓴다.

반드시 확인할 품질 범주: 보안, 개인정보, 접근성, 성능, 신뢰성, 복구, 관찰 가능성,
호환성, 국제화가 해당되는지.

출구: 누락과 중복이 검토된 요구사항 트리.

### 7. 정보 구조와 사용자 흐름

화면이나 상태를 노드로, 전이와 조건을 엣지로 표현한다. 행복 경로만 그리지 않는다.

- 진입과 종료
- 빈 상태와 최초 사용
- 로딩과 지연
- 입력 오류와 시스템 오류
- 권한 없음과 인증 만료
- 취소, 되돌리기, 중단 후 복귀
- 분기 조건과 반복
- 키보드·보조기술·축소 모션 경로

트리 뷰는 전체 구조, 디렉토리 뷰는 한 기능의 정책, 플로우 뷰는 상태 전이를 보여 주되 같은
ID를 사용한다.

출구: 모든 필수 요구사항이 한 흐름 또는 명시적인 비화면 동작에 연결된 상태.

### 8. 화면과 콘텐츠

화면 목적, 주요 행동 하나, 보조 행동, 필요한 정보, 상태별 문구를 먼저 정한다. 시각 방향이
필요하면 `asgard-freyja4`를 사용해 구조가 다른 세 방향을 만들고 사용자가 하나를 고른 뒤
구현한다. 장식보다 위계, 읽기 순서, 상태 피드백, 접근성을 우선한다.

출구: 선택된 화면 구조, 콘텐츠 초안, 상태 목록. 선택 전 이미지를 구현 사실처럼 취급하지
않는다.

### 9. 검증

각 수용 기준은 한 사용자가 한 조건에서 한 관찰 가능한 결과를 보게 쓴다. 다음을 수행한다.

- 요구사항 ↔ 흐름 ↔ 수용 기준 추적성 검사
- 모순, 고아 항목, 근거 없는 결정, 해결되지 않은 의존성 검사
- 대표 시나리오와 실패 시나리오 walkthrough
- 접근성·개인정보·보안·운영 위험 검토
- AI 제안과 사용자 결정의 경계 확인

출구: 검토 결과, 남은 위험, 검증 방법, 승인 또는 보류 결정.

### 10. 로드맵과 핸드오프

날짜를 먼저 채우지 않는다. 결과와 의존성 기준으로 Now / Next / Later를 만든 뒤, 실제
용량·소유자·외부 마감이 확인된 항목만 날짜를 가진다. 구현 단위는 수직으로 자르고 각 단위에
사용자 행동, 수용 기준, 검증 명령/증거, 선행 조건을 넣는다.

사용자가 구현을 요청하지 않았다면 여기서 멈춘다. 요청했다면 현재 저장소 관례의 명세와
퀘스트로 넘기고 Worker가 실행하게 한다.

출구: 누가 무엇을 어떤 근거와 기준으로 이어서 할지 재구성 없이 알 수 있는 상태.

## 변경 관리

결정 또는 요구사항이 바뀌면 먼저 영향 범위를 보여 준다. 변경 전/후, 이유, 승인자, 영향을
받는 요구사항·흐름·수용 기준·구현 단위를 기록한다. AI가 충돌을 제안할 수는 있지만 자동으로
기존 결정을 덮지 않는다.

## 필요한 스킬 배치

- 용어와 경계가 흔들리면 `domain-modeling`
- 실행해 봐야 결정되는 로직·화면이면 `prototype`
- 시각 구조·상태·접근성·그래픽이면 `asgard-freyja4`
- 최신 사용자/시장 신호가 실제 결정에 필요할 때만 조사 스킬
- 문서·슬라이드·시트·PDF 내보내기는 사용자가 형식을 요청했을 때만 해당 Office 스킬
- 구현 명세와 작업 분할은 사용자가 명시적으로 요청한 뒤 해당 워크플로

필요한 순간에 하나씩 로드한다. 전부 미리 로드하지 않는다.

## 완료 판정

“문서가 만들어졌다”는 완료가 아니다. 다음이 모두 참일 때만 기획 완료다.

- 핵심 문제와 목표가 근거에 연결됨
- 가정, 제안, 결정이 구분됨
- 필수 요구사항이 흐름·수용 기준에 연결됨
- 정상·빈·오류·권한·복구·접근성 상태가 다뤄짐
- 우선순위와 일정에 근거 또는 명시적 공백이 있음
- 미해결 위험과 결정권자가 보임
- 구현자가 대화를 재구성하지 않고 다음 단위를 시작할 수 있음
