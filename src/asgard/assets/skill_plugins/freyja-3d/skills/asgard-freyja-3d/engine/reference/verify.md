# 검증 — 무엇이 무엇을 증명하는가

3D 에서 가장 비싼 실패는 **코드가 성공적으로 실행되고 잘못된 형상을 내보내는 것**이다. 컴파일도 되고, 파일도 생기고, 예외도 없다. 잘못된 것은 형상뿐이다.

이 실패 모드는 문헌에서 반복 확인된다. CADCodeVerify(ICLR 2025)는 렌더 이미지에 대해 검증 질문을 만들어 스스로 답하게 하는 것만으로 점군 거리 7.3% 감소·성공률 5.0%p 상승을 얻었고, 3DCodeBench(2026)는 "성공적으로 렌더된" 결과조차 떠 있거나 끊어진 부품을 흔히 포함한다고 보고한다. 결론은 하나다: **되먹임 루프 없이는 형상 오류가 남는다.**

## 도구가 증명하는 것과 증명하지 못하는 것

| 도구 | 증명한다 | 증명하지 못한다 |
|---|---|---|
| `cad_build.py` | 스크립트 실행, 솔리드 존재, 부피·경계상자, 커널 유효성, 부품 간 간섭·간극 | 형상이 **요청한 물건인지** |
| `mesh_audit.mjs` | 수밀성, 감김 일관성, 살두께, 오버행, 셸 개수, 조형 공간 적합 | 기능적 강도, 사용성, 미관 |
| `scene_audit.mjs` | 파일 크기, 삼각형, 드로우콜, 텍스처 VRAM 추정, 압축 적용 | 실제 프레임률(기기에서 재야 한다) |
| `detect3d.mjs` | 알려진 정적 결함 패턴 | 실행 시 동작, 시각 품질 |
| `shoot.mjs` | 형상이 실제로 어떻게 생겼는지 | 아무것도 자동으로 판정하지 않는다 — **사람(또는 모델)이 이미지를 봐야 한다** |

마지막 줄이 핵심이다. 렌더는 판정이 아니라 증거다. 증거를 만들어놓고 열어보지 않으면 만들지 않은 것과 같다.

## 렌더 자기검증 절차

1. `shoot.mjs` 로 최소 4면(front, right, top, iso)을 뽑는다. 대칭이 중요하면 back/left 를, 인쇄 방향이 중요하면 `--highlight overhang` 을, 두께가 쟁점이면 `--highlight thick` 을 추가한다.
2. **이미지를 연다.**
3. 명세에서 **검증 질문 목록을 만든다.** 질문은 명세의 각 항목에서 기계적으로 유도한다:
   - "구멍이 판의 중앙에서 상단으로 10mm 위치에 있는가?"
   - "선반이 수직판과 직각으로 만나는가?"
   - "돌출부가 다른 부품과 겹치지 않고 떨어져 있는가?"
   - "바닥면이 평평해서 플레이트에 안정적으로 놓이는가?"
   - "요청에 없는 형상이 추가되지 않았는가?"
4. 각 질문에 **이미지를 보고** 예/아니오로 답하고, 아니오인 항목만 코드에서 고친다.
5. 고친 뒤 다시 1번으로. 3DCodeBench 는 다회차 정제가 성능을 올린다고 보고하지만, **같은 오류를 두 번 못 고치면 접근을 바꾼다**(형상 구성 순서 재설계, 도구 교체, 사용자 확인 요청).

## 회귀

파라미터를 바꾸면 다른 곳이 깨진다. 진단을 저장해두고 비교한다.

```bash
node engine/scripts/mesh_audit.mjs build/part.stl --process fdm --json > .asgard/.vanadis/3d/before.json
# ... 수정 ...
node engine/scripts/mesh_audit.mjs build/part.stl --process fdm --baseline .asgard/.vanadis/3d/before.json
```

부피가 의도 없이 변했다면 형상이 깨진 것이다. 오버행 비율이 갑자기 뛰었다면 방향이나 형상이 바뀐 것이다.

## 보고 규약

- 판정을 항목 이름으로 적는다: `수밀 PASS / 살두께 FAIL 0.42mm / 오버행 WARN 8.3% / 간섭 없음`.
- **실행하지 않은 검사를 통과로 적지 않는다.** 못 돌린 검사는 "미실행"이라고 적고 이유를 쓴다.
- 판정 기준을 낮춰서 통과시키지 않는다. 기준을 바꿔야 한다고 판단되면 그 근거(공정 변경, 벤더 데이터시트)를 함께 적는다.
- 자기 산출물에 대한 자기 점수는 "자기 보고"라고 적는다. 리뷰라고 부르지 않는다.
