# 성능 예산

예산은 협상 대상이 아니라 **설계 입력**이다. 만들고 나서 재는 것이 아니라, 만들기 전에 정하고 그 안에서 만든다.

## 기본선

`scene_audit.mjs` 가 이 값으로 판정한다(예산의 75%를 넘으면 WARN, 초과하면 FAIL).

| 항목 | 모바일 | 데스크톱 | 왜 |
|---|---|---|---|
| 다운로드 크기 | 5MB | 15MB | 3G/저속 네트워크에서 첫 렌더까지의 시간을 지배한다 |
| 화면 삼각형 | 150K | 1M | 정점 처리보다 대개 다른 병목이 먼저 온다 |
| **드로우콜** | 100 | 500 | **프레임을 결정하는 숫자.** 모바일에서 50 이하면 안전권 |
| 텍스처 VRAM | 50MB | 200MB | 초과 시 모바일에서 탭이 죽는다 |
| 최대 텍스처 변 | 1024 | 2048 | 화면 점유 크기를 넘는 해상도는 낭비다 |
| 프레임 시간 | 33ms(30fps) 중급기 | 16.6ms(60fps) | 상시 60fps 를 모바일 기준선으로 잡지 않는다 |

이 값은 일반 웹 경험 기준이다. 게임·구성기·전시 키오스크는 대상 기기를 특정해 다시 정한다.

## 측정

```bash
node engine/scripts/scene_audit.mjs public/model.glb --target mobile
```

정적 감사는 자산을 판정하고, **프레임률은 기기에서 재야 한다**. 브라우저 개발자 도구에서:

- CPU 4~6배 스로틀 + 모바일 뷰포트로 프레임 그래프를 본다.
- `renderer.info` 로 실제 드로우콜(`render.calls`), 삼각형(`render.triangles`), 텍스처·지오메트리 수(`memory`)를 읽는다. 이것이 진짜 숫자다.
- 긴 프레임의 원인을 본다: 셰이더 컴파일(첫 등장), GC(루프 내 할당), 텍스처 업로드(로딩 중), 오버드로우(반투명).

## 예산을 넘겼을 때 — 효과 순서

1. **드로우콜 병합**: `InstancedMesh`(같은 지오메트리), `BatchedMesh`(다른 지오메트리·같은 재질), 정적 배경 병합. 대개 여기서 가장 큰 이득이 나온다.
2. **텍스처 압축**: KTX2/Basis. VRAM 이 수 배 줄고 모바일 크래시가 사라진다.
3. **지오메트리 압축**: meshopt(디코드 빠름) 또는 Draco(압축률 높음). 다운로드 크기에 직접 효과.
4. **텍스처 해상도 하향**: 화면 점유 크기 기준으로 2048→1024→512. 눈으로 확인하며 내린다.
5. **재질 통합**: 재질 수가 곧 드로우콜 그룹 수다. 아틀라스로 묶는다.
6. **지오메트리 단순화**: 실루엣이 무너지기 직전까지. 자동 비율 하나로 전 자산을 처리하지 않는다.
7. **씬 축소**: 마지막 수단. 무엇을 뺄지는 사용자와 정한다 — 조용히 빼지 않는다.

## 로딩 예산

- 첫 페인트는 3D 를 기다리지 않는다. 히어로 콘텐츠는 모델 로딩 전에 보인다.
- 프로그레시브: 저해상도 먼저 → 고해상도 교체. `gltf-transform` 계열로 LOD 를 미리 생성해둘 수 있다.
- 실패 경로: 네트워크 실패·WebGL 미지원·저사양에서 **정지 이미지 폴백**을 만든다. 검은 캔버스를 남기지 않는다.

## 안 되는 조합 — 명세 단계에서 걸러야 한다

- 모바일 60fps + 실시간 그림자 + 반투명 다중 레이어 + 후처리 블룸
- 5MB 예산 + 4K PBR 텍스처 세트(알베도·노멀·러프니스·AO) 4개
- 100 드로우콜 + 개별 재질을 가진 오브젝트 300개

이런 요청은 만들기 전에 지적한다. 만들고 나서 "느리다"고 보고하는 것은 늦다.
