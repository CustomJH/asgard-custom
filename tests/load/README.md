# Project memory load harness (k6, Docker) — 실측 기록

**실행 자산은 여기 없다.** 이 디렉터리의 내용물은 이 문서 하나다. 아래 표를 만든 시나리오
둘(`recall` · `saturate`)은 `src/asgard/assets/k6_kit/scenarios/` 가 정본이고, `asgard k6 sync`
가 그것을 재는 프로젝트의 `.asgard/k6/kit/` 로 내려 `asgard k6 run` 이 `docker/asgard-k6/` 의
이미지로 돌린다. 문서만 남긴 이유는 표다 — 아래 실측은 `src/asgard/project_memory/` 의
`documents.py`·`ingest.py` 와 `tests/test_project_documents.py` 가 레인을 가른 근거로 인용한다.

이 경로는 어디서도 자동으로 돌지 않는다. 실엔진 검증(`tests/test_k6.py`)은 `ASGARD_K6_DOCKER=1`
일 때만 돌고 기본 스위트에서는 건너뛴다. 그래서 아래 날짜는 **그날 그 스택의 값**이지 현재
상태의 보증이 아니다 — 다시 재려면 `asgard k6 selftest` 가 녹색인지부터 본다.

프로젝트 메모리 backend 는 팀이 공유하는 원격 서비스다. 한 사람의 지연은 doctor 가 보지만,
**여러 사람이 동시에 회수할 때 무슨 일이 나는지**는 재 보지 않으면 알 수 없다. 그 자리를 여기서 잰다.

회수 경로만 잰다. 등록은 사람이 승인할 때 한 번이고, 회수는 대화마다 돈다.

## 실행

```bash
asgard k6 run saturate --target http://host.docker.internal:18890 --env BANK=<bank>
```

`recall` 은 1→50 VU 램프(임계값 판정), `saturate` 는 1·2·5·10·20 VU 계단(포화점 탐색).
빈 뱅크에 걸면 의미가 없다 — `asgard memory project-sync --all --inventory` 로 채운 뱅크를 쓴다.

두 시나리오는 이제 `asgard-k6` 레인이 소유한다(여기 있던 `.js` 두 개를 그리로 옮겼다).
손으로 `docker run -v ...` 를 치던 자리가 사라졌고, 이미지·부하 형상·k6 판이 실행마다
보고서에 새겨진다. 그 하네스가 참을 말하는지는 `asgard k6 selftest` 가 따로 판정한다 —
아래 표들은 그 검사가 녹색인 하네스에서 얻은 값이어야 근거다.

## 실측 (Hindsight 0.8.3 · Docker · M-series · 2026-07-28)

| 동시 VU | p95 | 평균 |
|---|---|---|
| 1 | 0.51s | 0.48s |
| 2 | 0.76s | 0.71s |
| 5 | 1.80s | 1.45s |
| 10 | 3.47s | 2.82s |
| 20 | 6.22s | 5.52s |
| 50 | 14.98s | 6.82s |

처리량은 VU 와 무관하게 **~2.9 req/s 로 평평하다** — 지연 증가는 전부 큐 대기다.
요청 모양은 원인이 아니다: budget(low/mid)·include(chunks/entities)·max_tokens 를 바꿔도
단일 요청은 0.47~0.58s 로 같았다.

### 재실측 (같은 날, 같은 스택 · 뱅크 `hvami-test` · 2회 반복)

| 동시 VU | p95 (1회) | p95 (2회) | 위 표 대비 |
|---|---|---|---|
| 1 | 0.78s | 0.85s | 1.6배 느림 |
| 2 | 1.26s | 1.25s | 1.6배 |
| 5 | 2.89s | 3.21s | 1.7배 |
| 10 | 6.78s | 6.83s | 2.0배 |
| 20 | 13.14s | 14.35s (max 15.17s) | 2.2배 |

처리량 **1.68~1.73 req/s** (위 표의 ~2.9 가 아니다). 두 회차가 서로 재현되고 서버는
유휴(CPU 0.25%)에서 출발했으므로 잡음이 아니다 — 위 표와 아래 표는 **다른 뱅크·다른 코퍼스**다.
그러니 두 수치를 하나의 "성능"으로 합치지 마라. 이 하네스가 재는 것은 인스턴스가 아니라
**인스턴스 × 뱅크**다.

읽는 법 (정정): 기본 timeout 15s 기준으로 20 VU 는 **여유가 아니라 경계**다 — 재실측 2회차의
max 가 15.17s 로 이미 넘었다. 위 표의 "~20건까지 여유"는 그 코퍼스에서만 성립한다.
`recall.js` 의 1→50 VU 램프는 선언된 임계값 `p(95)<3000` 을 **p95 29.34s 로 크게 넘긴다**
(오류는 0%, 전부 200 — 실패가 아니라 줄서기다).

### 이 하네스가 못 재는 것

부하가 아니라 **뱅크의 그래프 모양**이 지배적이다. 같은 서버·같은 질의·같은 예산에서:

| 뱅크 | units | links | 노드당 | 단일 회수 |
|---|---|---|---|---|
| `hvami-test` | 11 | 26 | 2.4 | 200, 1s |
| `proj-ing-f4ad8c` (326KB 문서 2개) | 44 | 1,340 | 30.5 | **무응답, 45s 타임아웃, 8GiB 상한 고착** |

VU 1 에서도 그렇다. 그러니 이 표들을 "동시 사용자 N 명까지 된다"로 읽기 전에, 대상 뱅크가
어느 쪽 모양인지부터 봐야 한다 — 조밀한 뱅크는 **한 명에게도** 안 된다.

## 정정 — 원인은 링크 밀도가 아니었다 (26-07-28 3차, 실서버 계측)

위 표를 "조밀한 그래프가 회수를 죽인다"로 읽었는데 **틀렸다**. 버려도 되는 뱅크를 새로
파서 변수를 하나씩 갈라 재 보니 그래프는 용의자가 아니었다. 서버 로그가 단계별 시간을
그대로 준다:

```
[2] Parallel retrieval: semantic=3, bm25=3, graph=0(0.003s) … 0.024s
[4] Reranking [cross-encoder]: 3 candidates scored in 20.675s   ← 회수 시간의 99%
```

**비용은 후보 수 × 후보 길이**이고, 그걸 무는 것은 CPU 크로스 인코더(bge-reranker-v2-m3)다.
같은 그래프 모양(3노드·9링크)에서 언어만 바꾸면:

| 뱅크 | 내용 | nodes/links | 회수 | 적중 |
|---|---|---|---|---|
| `hvami-test` | 영어 실물, 작은 청크 | 11 / 27 | **1.0s** | 6 |
| `cal-en` | 영어 합성, 8000자 청크 | 3 / 9 | 5.3–7.0s | 1 |
| `cal-smoke` | 한국어 합성, 8000자 청크 | 3 / 9 | **20–21s** | 0 |

노드 3개짜리 뱅크가 20초다. 밀도로는 설명되지 않는다. 한국어가 같은 글자 수에서 토큰이
훨씬 많아 후보 하나가 그만큼 비싸질 뿐이다.

### 청크 크기를 갈라 재기 (문서 96,000자 고정, 한국어 실물 산문)

| chunk | nodes | links | 노드당 | 회수 | 적중 |
|---|---|---|---|---|---|
| 8000 | 13 | 109 | 8.4 | 33s → **서버 사망** | 0 |
| 4000 | 32 | 541 | 16.9 | 57–67s | 1 |
| 2000 | 74 | 1,480 | 20.0 | 51–53s | 1–2 |
| 1000 | 168 | 3,360 | 20.0 | 56–63s | 3–5 |
| 500 | 363 | 7,260 | 20.0 | 41–46s | **9–10** |

**링크 7,260개짜리 구성이 가장 건강하다** — 사망한 뱅크(1,340개)의 5배인데 적중이 10건이다.
밀도 가설은 여기서 끝난다. 그리고 8000자 청크의 적중 0은 우연이 아니다: 한국어 8000자
단위 하나가 회수 예산 `max_tokens=2048` 을 넘어 토큰 필터에서 통째로 버려진다 — **리랭크
비용은 다 물고 결과는 0건**인 쓰기 전용 경로였다.

작은 청크는 품질을 되살리지만(0→10) 지연은 41~67s 로 평평하다: 후보가 늘어난 만큼
하나가 싸져서 총합이 그대로다. 즉 **96,000자 한국어 문서는 어떤 청크 크기로도 이 배포에서
회수되지 않는다.**

`mem_limit` 도 다시 봐야 한다. "상한을 걸면 컨테이너가 더는 안 죽는다"고 적었던 것 역시
**틀렸다** — 8g 를 건 채로 이 실험을 돌리는 동안 `RestartCount` 가 1→4 로 올랐다.
커널 OOM 킬은 아니고(`OOMKilled=false`, `ExitCode=0`) 프로세스가 스스로 끝나며, 그 몇 초
동안 **다른 뱅크의 회수도 같이 죽는다**(`RemoteDisconnected`).

### 상한은 어디인가 (청크 1000 · 문서 크기를 올려 가며)

문턱은 임의값이 아니라 제품이 이미 정한 값이다: `memory_context.project_recall_note` 는
턴 시작 주입을 `operation_timeout = min(cfg timeout, 5)` 로 자른다. 5초를 넘는 회수는
느린 게 아니라 **주입면에서 존재하지 않는다**.

| chars | units | links | 회수 | 적중 | ≤5s |
|---|---|---|---|---|---|
| 2,000 | 3 | 9 | 0.9s | 3 | ✓ |
| 4,000 | 5 | 25 | 2.0s | 3 | ✓ |
| 8,000 | 11 | 121 | 4.4s | 2~3 | ✓ |
| 12,000 | 16 | 256 | **6.0s** | 1 | ✗ |
| 16,000 | 25 | 500 | 10.4s | 3~4 | ✗ |
| 48,000 | 77 | 1,540 | 29.6s | 3~4 | ✗ |

회수 시간 ≈ **0.38s × units**. 품질은 어느 크기에서도 3~4건으로 멀쩡하다 — 큰 문서가
그래프 레인에서 탈락하는 이유는 못 찾아서가 아니라 **제때 못 돌아와서**다.

12,000자 줄은 asgard 클라이언트(`HindsightBackend.recall`) 왕복으로 잰 값이고, 여기서
예측 모형의 결함도 드러났다: 청크 **상한**(1000)으로 나누면 12 units 인데 서버는 16개를
만든다. 서버가 상한을 채우지 않고 경계에서 자르기 때문이다. 그래서 예측은 실측 평균
단위 크기(`EFFECTIVE_UNIT_CHARS = 620`)로 나눈다 — 모든 실측점에서 예측이 실제를 밑돌지
않는 쪽으로 고른 값이다.

### 결론 — 레인을 가른다

`asgard memory project-ingest` 가 등록 **전에** unit 수를 예측하고 상한
(`ingest.GRAPH_UNIT_CEILING` = 13 units ≈ 8,060자)을 넘으면 로컬 레인으로 보낸다:

| 레인 | 정본 | 검색 | 팀 공유 |
|---|---|---|---|
| graph | 승인 후 backend 뱅크 | 서버 그래프 회수 | 뱅크 |
| local | `.asgard/memory/documents/` | 로컬 FTS5 (파생, 재생성 가능) | Git 커밋 |

넘겼을 때의 비용은 대칭이 아니다. 밑돌면 문서 하나가 로컬로 가고 여전히 검색되지만,
넘치면 서버 프로세스가 종료돼 **다른 뱅크의 회수까지** 같이 죽는다.
`--lane graph` 로 덮을 수 있다 — 자동은 기본값이지 구속이 아니다.

이미 조밀해진 뱅크는 이 게이트가 되살리지 못한다. 뱅크를 새로 만들고
`asgard memory project-ingest <문서>` 를 다시 돌려 로컬 레인으로 받는 것이 유일한 회복 경로다.

### 재현

`scratchpad` 하네스가 아니라 이 표를 다시 만들려면: 버릴 뱅크를 새로 파고(`PUT
/v1/default/banks/<id>`), `ingest.STRATEGIES` 를 심고, 문서를 넣고, `POST
/memories/recall` 을 `src/asgard/assets/k6_kit/scenarios/recall.js` 와 **같은 요청 모양**으로
부른다. 서버 로그가
단계별 시간(`[2] Parallel retrieval` / `[4] Reranking`)을 그대로 찍어 주므로 어느 단계가
비용인지는 추측할 필요가 없다.
