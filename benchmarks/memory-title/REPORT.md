# 제목 벤치 — 기억 한 장의 제목을 무엇으로 삼을 것인가 (26-08-19)

## 질문

개인 기억 50장 중 49장이 본문 첫 줄을 베낀 제목을 달고 있었다. 낱말 한가운데서 끊기던 것은
고쳤지만 고친 제목도 여전히 본문의 앞부분이다. 다른 기억 시스템은 이 자리를 다르게 지난다 —
mem0·Zep 은 제목을 아예 두지 않고 자립 사실 문장이 곧 단위이며, A-MEM(arXiv 2502.12110)과
cognee 는 LLM 이 짓는 별도 필드를 둔다. A-MEM 은 그 필드가 무엇을 담을지를 갈래로 지정하고
(주제·논점·대상) 화자 이름과 시간을 빼라고 못박는다.

물음 둘. **① LLM 이 제목을 짓게 하는 것이 실제로 값이 있는가.** ② A-MEM 의 지시 방식이 지금
우리 지시문보다 나은가.

## 방법

`harness.py`. 오딘의 실제 기억 48장(본문 40자 미만 제외)을 읽기만 하고, 팔마다 임시 홈에
색인한다. 시맨틱은 끈다 — 켜면 제목의 몫과 임베딩의 몫이 섞인다.

네 팔. 본문도 모델도 같고 제목 짓는 방식만 다르다.

| 팔 | 제목을 만드는 것 |
| --- | --- |
| `derived_legacy` | 화자를 떼기 전의 파생기 (26-08-19 이전 동작, 벤치가 재현용으로 들고 있다) |
| `derived` | `store.derive_title` — 지금 저장소가 제목 없이 저장될 때 하는 일 |
| `current` | 지금 도구 다섯 표면이 모델에게 주는 지시문 |
| `amem` | A-MEM 의 두 규칙을 옮긴 지시문 |

**낱말이 본문에 있는지는 부분문자열 포함으로 본다.** 색인이 실제로 그렇게 맞추기 때문이다 —
`recall/search.py` 의 `matched = [w for w in scan_words if w in hay]` 이고, 그 위에 조사·어미를
뗀 변형까지 후보에 넣는다. 이 자를 안 쓰면 `baseline_checks가` 와 `baseline_checks` 가 남남이
되어 색인이 같다고 보는 낱말을 계기만 새 낱말로 센다 (아래 "계기가 세 번 거짓말했다").

## 결과 (계기 5판, 모델 팔은 3회 실행)

| 축 | derived_legacy | derived | current | amem |
| --- | --- | --- | --- | --- |
| `body_prefix` | 1.000 | 0.354 | 0.007 | 0.000 |
| `body_substring` ↓ | 1.000 | **1.000** | 0.007 | 0.007 |
| `head_overlap` ↓ | 1.000 | 0.997 | 0.612 | **0.596** |
| `speaker_prefix` ↓ | 0.646 | **0.000** | 0.014 | 0.021 |
| `novel_words` ↑ | 0.000 | 0.000 | 0.320 | **0.356** |
| `distinct10` ↑ | 0.667 | 0.854 | 0.924 | 0.917 |
| `chars` ↓ | 61.3 | 59.0 | **21.9** | 24.9 |
| `summary_recall@3` ↑ | 0.032 | 0.032 | 0.101 | 0.066 |
| `indexed_recall@1` ↑ | 1.000 | 1.000 | 1.000 | 1.000 |

`body_prefix` 에 화살표가 없는 이유는 아래 F2 에 적었다 — 화자를 떼면 정의상 떨어지므로
혼자서는 개선을 뜻하지 않는다. "본문에서 온 것인가" 를 그대로 말하는 축은 `body_substring` 이다.

## 판정

**① LLM 이 짓는 제목은 파생 제목보다 확실히 낫다. 이건 갈릴 여지가 없다.**

파생 제목은 48장 **전부**가 본문의 문자 그대로의 부분문자열이고(`body_substring` 1.000),
색인에 더하는 낱말이 **0.000** 이다. 하나도 없다. 본문에서 베껴 왔으니 당연하고, 그 칸은
같은 낱말을 한 번 더 세는 것 말고 하는 일이 없었다. 모델이 지으면 신규어가 0.32~0.36 이
되고 `body_substring` 은 0.007 로 떨어진다. 길이도 61.3자에서 22자로 줄어 48장 기준 약
1,900자를 주입면에서 돌려받는다. 어제 `title` 을 도구 스키마의 필수 칸으로 올린 결정이 이
숫자로 뒷받침된다.

**② `current` 와 `amem` 은 이 벤치로 가릴 수 없다. 그래서 지시문을 바꾸지 않는다.**

축이 서로 반대쪽을 가리킨다.

- `amem` 이 3판 모두 이기는 축: `novel_words`(0.320 → 0.356), `head_overlap`(0.612 → 0.596)
- `current` 가 3판 모두 이기는 축: `chars`(21.9 → 24.9)
- 사실상 동률: `distinct10` (0.924 vs 0.917, 3판 중 2판 동점)

차이의 크기도 작다 — 신규어 3.6%p, 길이 3자. `summary_recall@3` 은 `current` 가 높지만
그 축은 아래 "못 재는 것" 에 적은 이유로 판정에 못 쓴다.

바꾸지 않는 이유는 **`amem` 이 졌기 때문이 아니라 이겼다는 증거가 없기 때문이다.** 지시문을
다섯 표면에서 바꾸는 값은 이 차이보다 크다. `amem` 이 신규어와 독립성에서 조금 앞선 것은
사실이고, 제목 필드를 색인에서 분리하는 날이 오면 그 축이 지금보다 무거워지므로 그때 다시
재야 한다.

**③ 화자 접두사를 떼는 것은 값이 있다.** A-MEM 의 두 규칙 중 이쪽은 살아남았다. 48장 중
31장이 `오딘은…` 으로 시작했고, 그러면 목록에서 앞 세 글자가 늘 같다. 파생기에서 그 조각만
떼자 `distinct10` 이 0.667 → 0.854 로 올랐다. `store.strip_speaker` 로 반영했다.

두 가지를 하지 않는다. 첫 글자를 대문자로 올리지 않는다 — 바뀐 31장 중 8장이 `asgard-seal`·
`justfile`·`helios-application` 처럼 실제 명령과 저장소 이름으로 시작하고, 올리면 그 이름이
더는 그 이름이 아니다. 그리고 조사가 없으면 떼지 않는다 — `사용자 정의 필드`,
`사용자 인터페이스` 는 화자가 아니라 복합명사이고, 자르면 남는 것이 다른 말이 된다.

## 실제 기억에 적용한 결과

`asgard memory lint --fix` 를 두 번 돌렸다. 먼저 화자 제거를 반영해 28장(백업
`20260819T121035Z-before-strip-speaker`), 그다음 아래 F4 를 고치고 5장(백업
`20260819T123756Z-before-truncated-retitle`)이다. 두 번 다 본문과 slug 은 안 바뀌었다.

지금 50장 전체: `distinct10` **0.860**, `speaker_prefix` **0.000**, `title-truncated` **0**.
화자로 시작하는 제목은 남지 않았다. 벤치가 48장에서 예측한 `distinct10` 0.854 와 실제 0.860 이
사실상 같다.

첫 번째 적용 뒤에는 다섯 장이 `오딘은…` 으로 시작한 채 남아 있었다. 그때 이 자리에는 그것이
`_SPEAKERLESS_MIN` 때문이라고 적혀 있었는데 **틀렸다** — 다섯 장 모두 화자를 떼면 68~79자가
남아 12자 하한 근처에도 안 갔다. 진짜 이유는 F4 였고, 열려 있는 구멍을 설계 한계로 적은
것이라 그 판이 FAIL 을 받았다.

## 계기가 세 번 거짓말했고, 그 검사가 네 번째를 찾았다

이 벤치에서 가장 값나가는 기록은 표가 아니라 이 절이다. 앞의 셋은 **계기가 초록인 채로**
결론을 바꿨고, 넷째는 계기가 아니라 배포 코드의 결함인데 같은 검사에서 나왔다.

**F1 — 화자 판정이 0 을 냈다.** `^\s*(오딘|사용자|…)\b` 로 셌는데 한국어는 조사가 낱말 문자라
`오딘은` 에서 경계가 안 잡힌다. 48장 중 31장이 화자로 시작하는데 계기는 0.000 을 보고했고,
그대로 믿었으면 "화자 접두사 문제는 없다" 는 결론이 나갔다. 지금은 파생기가 실제로 떼는
자(`store._SPEAKER_HEAD`)와 같은 것으로 센다 — 자를 두 벌 두면 또 갈린다.

**F2 — `derived` 팔의 정의가 도중에 바뀌었는데 이름이 같았다.** 화자 제거를 반영한 뒤의 판과
그 전의 판이 한 평균에 섞여 `speaker_prefix 0.575` 같은 없는 값이 나왔다. 레코드마다 팔이
부르는 코드의 해시(`impl`)를 적어 갈랐다.

**F3 — 신규어를 색인이 안 쓰는 자로 셌고, 그 숫자가 결론을 뒤집었다.** `_content_words` 는
`re.split(r"[^\w가-힣]+", …)` 하나라 `baseline_checks가` 와 `baseline_checks` 를 다른 낱말로
센다. 색인은 부분문자열로 맞추므로 그런 낱말은 새로 들어가지 않는다. 두 자의 차이:

| | 집합 교집합 | 색인 규칙 | 판별 |
| --- | --- | --- | --- |
| `current` | 0.598 | **0.320** | 0/3 |
| `amem` | 0.550 | **0.356** | 3/3 |

부호가 뒤집힌다. 이 판정의 첫 판은 이 숫자를 A-MEM 기각의 첫째 근거로 앞세웠고, 그것이
FAIL 사유였다. `head_overlap` 도 같은 이유로 뒤집혔다(0.353/0.405 → 0.612/0.596). 고친 뒤
남은 결론은 위 ②다 — 기각이 아니라 "가릴 수 없다".

**F4 — `retitle` 이 가장 나아질 제목을 통째로 빠뜨렸다.** `pages._stale_title` 이
`first.startswith(title)` 로 "본문에서 베낀 제목인가" 를 판정하는데, 잘려서 말줄임표가 붙은
제목은 본문의 접두사가 아니게 되어 이 판정을 못 지난다. 그래서 가장 손볼 값이 큰 제목이
`lint --fix` 의 사정권 밖에 있었다. 비교 전에 표시를 떼도록 고쳤고 남아 있던 다섯 장이
`speaker_prefix` 0.000 으로 닫혔다. 이것은 계기가 아니라 배포 코드의 결함인데, 계기 절에 같이
적는 이유는 **발견 경로가 같기 때문**이다 — 보고서가 적은 수치를 실제 데이터에 다시 걸어 보는
검사에서 나왔다.

계기를 고친 뒤 모델을 다시 부르지 않았다. `--recompute` 가 기록된 제목으로 축만 다시 센다.
다시 부르면 온도 손잡이가 없어 제목이 달라지고, 계기 수정의 몫과 모델의 흔들림이 섞인다.

## 이 벤치가 못 재는 것

`summary_recall@3` 은 48장 중 1~6장만 맞히는 자리라 한 장이 들락날락하면 0.02 가 움직인다.
모델을 안 부르는 `derived` 팔조차 같은 코드로 0.021 과 0.042 사이를 오갔다. 표의
`current 0.101 vs amem 0.066` 은 6개 값 중 4개만 그 부호이고 2개는 동점이라, 이 축 하나로는
아무것도 못 세운다.
`indexed_recall@1` 은 네 팔 모두 1.000 으로 천장이라 무회귀 확인 말고는 안 가른다 — 질의가
드문 낱말 셋이라 너무 쉽다.

그 밖에 못 재는 것: 제목이 사람에게 읽기 좋은가(주관이라 세지 않는다), 실제 세션에서 모델이
얼마나 잘 짓는가(여기서는 본문만 주지만 실제 도구 호출은 대화 맥락 안에 있다), 다른 위키에서도
같은 값이 나오는가(코퍼스가 한국어 48장이다). `memory.manager.complete` 에 온도 손잡이가 없어
같은 팔을 다시 돌리면 제목이 달라진다 — 그래서 판정은 3판 내내 같은 부호가 나온 축으로만 세웠다.

## 다시 돌리려면

```
uv run --no-project python benchmarks/memory-title/harness.py --repeat 3
uv run --no-project python benchmarks/memory-title/harness.py --arms derived_legacy,derived   # 모델 없이
uv run --no-project python benchmarks/memory-title/harness.py --recompute                     # 축만 다시
```

결과는 `results.jsonl` 에 덧붙는다. 읽을 때 `instrument == 5` 로 거른다 — 1·2 판은 F1·F2 가
살아 있던 계기이고, 3 판은 F3 가 살아 있던 계기다. 나란히 읽으면 안 된다.

`instrument 5` 레코드는 팔당 두 벌이다 — `--recompute` 를 두 번 돌렸다(모델 팔 6건씩, 파생 팔
2건씩). 입력이 같은 제목이라 결정론 축은 두 벌이 글자까지 같고, `summary_recall@3` 만 색인 쪽
잡음으로 갈린다(위 "못 재는 것" 참조). 그래서 표의 회수 행만 모든 레코드의 평균이고 — 모델 팔은
6개, 파생 팔은 2개다 — 나머지 행은 두 벌이 같은 값이라 그대로다.
