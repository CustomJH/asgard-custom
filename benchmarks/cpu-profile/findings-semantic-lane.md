# 시맨틱 레인 — 1.9GB 는 무엇을 사는가 (2026-08-14)

`ASGARD_MEMORY_NO_DOWNLOAD=1`(현재 훅 기본값)은 **1.90GB·1.5초를 아끼고 회수 hit@1 을
6/12 → 2/12 로 떨어뜨린다.** 12질의 중 2건은 아예 빈 회수가 되고, 그중 하나는 개인 기억 주입
블록 자체가 안 실린다. 1.9GB 의 정체는 라이브러리가 아니라 모델 하나이고, 디스크 캐시가 이미
있어도 **프로세스마다 전액**이다.

계측만 했다 — 소스도 훅도 기본값도 안 고쳤다.

## 1. 플래그가 소스에서 무엇을 가르는가

읽는 자리는 **하나뿐**이다 — `src/asgard/memory_semantic.py:201` 의 `_DEADLINE_ENV`, 판정은
같은 파일 303행 `embedder()` 안의 `deadline_bound()`.

```
if deadline_bound():
    _CACHE["loaded"], _CACHE["fn"], _CACHE["dim"] = True, None, 0
    return None
```

임베더가 **아예 안 선다** — 캐시된 모델만 쓰는 것도, 다른 레인으로 떨어지는 것도 아니다.
`_CACHE["loaded"]` 갈래가 그 위에 있어서 이미 임베더를 올린 프로세스(네이티브 루프, 사람이 치는
CLI)는 이 판정에 안 걸린다. 값을 무는 것은 **프롬프트마다 새로 뜨는 훅 자식**뿐이다.

회수 레인은 넷 + 2단계다 (`src/asgard/memory/recall/search.py`):

| 레인 | 플래그 켜짐 (현재 훅) |
|---|---|
| ① FTS5 trigram | 그대로 |
| ② 정본 스캔 | 그대로 |
| ③ 시맨틱(코사인) | **통째로 빠짐** — `sem.active()` False 라 블록 미진입, `sem_order=[]` |
| ④ 그래프 PPR | 돌지만 **시드가 줄어든다** — seed 가 ①②③ 의 RRF 합인데 ③ 이 0 |
| ⑤ 구절 리랭크(2단계) | **통째로 빠짐** — `rerank.py:284` 가 `not sem.active()` 면 `[], 0.0` |

플래그 하나가 5개 계산 단계 중 2개를 끄고 1개의 입력을 줄인다.

## 2. 품질 대조 — 12질의, 이 저장소의 실제 개인 기억 40페이지·벡터 40행 전수

`memory.query(k=5, track=False, explain=True)` 를 두 프로세스로. `track=False` 인 이유는 계측이
오딘의 usage 카운터를 올리면 안 되기 때문이다.

| 질의 | 정답 순위 (플래그 ON) | 정답 순위 (플래그 OFF) |
|---|---:|---:|
| 판정자가 느린 진짜 원인 | 4 | 3 |
| 훅 파일이 두 자리로 갈라져 있다 | 1 | 1 |
| 승인 없이 기억을 저장하고 싶다 | **없음** | 3 |
| 다크 모드 배경 색 단계 | 3 | 2 |
| 번역 키가 로케일마다 빠지면 | 1 | 1 |
| CPU 를 너무 많이 쓴다 | 2 | **1** |
| 가드 정규식이 오탐을 낸다 | 4 | 2 |
| 릴리즈 버전 번호 규칙 | 2 | **1** |
| how do I make the verifier faster | 3 | 3 |
| what does Odin call himself | **없음** | **1** |
| 메모리 회수가 오래 걸린다 | 4 | 2 |
| 에이전트 배차 기록이 비어 있다 | 3 | **1** |

- **hit@1 2/12 → 6/12, hit@5 10/12 → 12/12. 퇴행 0건** — 플래그를 끈 쪽이 더 나쁜 질의는 없다.
- 결과가 완전히 같은 질의는 12 중 **1건**(영어 질의 하나, ①②④ 만으로 같은 순위). 나머지 11건은
  순서가 바뀌거나 다른 문서가 들어온다.
- 순서만 바뀌는 것이 아니다. `승인 없이 기억을 저장하고 싶다` 는 정답 페이지가 시맨틱 켜짐에서만
  후보에 들어온다 — 어휘로는 한 낱말도 안 겹친다.
- 훅이 실제로 **주입하는 문장**으로도 대조했다(`asgard memory recall --json`):
  `what does Odin call himself` 는 플래그 켜짐에서 `<memory-recall scope="personal">` 블록이
  통째로 없고, 끄면 peer card 와 이름 페이지가 실린다. 회수 0 이 아니라 **주입 0** 이다.

## 3. 자원 — 전/후 번갈아, `/usr/bin/time -l`

| 실행 | n | 벽시계 min / median | RSS min / median |
|---|--:|---|---|
| `memory recall` 시맨틱 켜짐 (1차) | 5 | 1.320s / 1.320s | 1,951.4MB / 1,951.4MB |
| `memory recall` `NO_DOWNLOAD=1` (1차) | 5 | 0.110s / 0.120s | 48.1MB / 48.2MB |
| `memory recall` 시맨틱 켜짐 (2차) | 7 | 1.590s / 1.690s | 1,950.5MB / 1,951.5MB |
| `memory recall` `NO_DOWNLOAD=1` (2차) | 7 | 0.130s / 0.150s | 48.2MB / 48.4MB |

| `memory snapshot` `NO_DOWNLOAD=1` | 3 | 0.060s / 0.060s | 32.7MB / 32.7MB |

두 차수 사이 벽시계 차이(1.32 vs 1.69)는 기계 소음이다 — 그 사이에 GB 단위 로드를 반복해 페이지
캐시를 흔들었다. **RSS 는 12회 내내 1,950.5~1,953.6MB 로 안 흔들린다.**

읽어 둘 것 둘. **`snapshot` 은 플래그와 무관하다**(32.7MB 양쪽 동일) — 훅 자식 넷 중 값을 무는
것은 `recall` 하나이고, 앞선 문서의 32.80MB 는 플래그 덕이 아니라 그 명령이 임베더를 안 여는
것이다. 그리고 한 프로세스 안에서는 로드가 1.10초 **한 번**이고 그 뒤 질의는 3.7~5.0ms 다 —
값 전부가 프로세스 경계에 있다.

## 4. 1.9GB 의 내역 — 임포트 계단 (`HF_HUB_OFFLINE=1`, 3회 최솟값)

| 단계 | RSS | 증분 |
|---|---:|---:|
| 맨 파이썬 | 16.0MB | — |
| `+ import huggingface_hub` | 17.6MB | **+1.6MB** |
| `+ import model2vec` (numpy·tokenizers 포함) | 45.0MB | +27.4MB |
| `tokenizer.json` 만 (`Tokenizer.from_file`, 어휘 500,353) | 784.4MB | +739MB |
| `model.safetensors` 만 (`(500353, 256) float32` = 명목 488.6MB) | 1,037.3MB | +992MB |
| `StaticModel.from_pretrained` + `encode` | **1,943.2MB** | — |

**앞선 지목이 반은 틀렸다.** `huggingface_hub` 는 1.6MB 다. 값은 라이브러리가 아니라 **모델
하나**(`potion-multilingual-128M`)이고, 그 안에서도 어휘 50만 항목이 두 번 값을 낸다 —
토크나이저 약 784MB, 임베딩 행렬 약 1,037MB(디스크 489MB 를 읽으며 대략 두 배로 부푼다).

**매번 드는 값이다.** 모델은 이미 디스크에 있고(`~/.cache/huggingface/hub/…potion-multilingual-128M`,
1.0GB) 위 수치가 전부 캐시 있는 상태의 값이라, 두 번째 호출이 싸지는 지점이 없다. 같은
프로세스에서 두 번 로드하면 3,025MB 로 거의 두 배가 된다 — mmap 공유가 아니라 매번 익명
메모리에 펼친다. 프로세스 안에서만 `_CACHE` 가 그걸 막는다.

같은 계열 다른 모델(전부 이미 캐시됨, 3회 최솟값): `potion-base-8M` 141.0MB·0.67s,
`potion-retrieval-32M` 345.1MB·0.73s, `potion-multilingual-128M` 1,777MB·2.50s. 작은 쪽이 12배
싸지만 `memory_semantic.py` 머리의 26-07-27 실측이 그 둘의 한국어 판별력을 **음수**로 적어 뒀다 —
값만 보고 갈 수 있는 자리가 아니고, 차원이 달라 `reindex` 도 따라온다.

## 5. 훅 경로 점검

- **거는 자리는 하나다.** `src/asgard/hooks/memory_activate.py:241` — `main()` 안, 네
  자식(`recall`·`snapshot`·`sync-turn`·`tick`) 어느 갈래보다 **앞**이라 env 상속으로 전부 덮인다.
  배포본 `.claude/hooks/memory-activate.py` 의 같은 줄과 바이트 동일.
- **다른 훅은 이 레인에 안 닿는다.** `src/asgard/hooks/*.py` 전수 grep 에서 메모리 명령을 띄우는
  훅은 `memory_activate` 하나다.
- **의도된 구멍이 하나 있고 그건 실재한다.** `src/asgard/memory/norn/auto.py:224` 의
  `spawn_pass()` 가 `detached_env()` 로 표식을 **떼고** 자식을 띄운다 — 안 떼면 위키를 쓰면서
  벡터를 안 만들어 `vec_coverage` 가 썩기 때문이다(근거는 그 함수 docstring). 그 자식은 Stop 훅의
  `memory tick` 에서 나오고 후보가 넷이다. 개인 페이지를 쓰는 패스는 `_vec_upsert` → `active()`
  에서 **전액 1.9GB 를 문다.** 사람이 기다리는 경로 밖이지만 같은 기계이고, 한 Stop 에서 여럿이
  동시에 뜰 수 있다. 이건 안 쟀다 — 돌리면 오딘의 위키가 바뀐다.
- 네이티브 루프와 사람이 치는 `asgard memory *` 는 원래 플래그 밖이다(모듈 주석이 그렇게 적어
  뒀다). 수명이 길어 한 번만 문다.

## 6. 못 잰 것

- 분리 스폰 패스 넷이 실제로 임베더를 여는지, 얼마나 자주 due 인지 — 실행이 곧 위키 변경이라
  소스 판독까지만.
- 첫 내려받기(약 1GB·수십 초) — 캐시가 이미 있고, 네트워크로 GB 를 끌어오지 않았다.
- 여러 훅 프로세스가 겹칠 때의 동시 최대 RSS.
- 품질 대조는 이 저장소의 40페이지·12질의다. 벤치가 아니라 실사다 —
  `benchmarks/hybrid-search` 의 100페이지 코퍼스는 안 돌렸다.
- 계측 중 `asgard memory recall` 을 24회 돌려 개인 기억의 **노출 카운터**가 그만큼 올라갔다(훅이
  프롬프트마다 하는 것과 같은 쓰기). `query` 쪽 usage 는 `track=False` 라 안 건드렸다.

## 오딘이 정할 것

**기본값은 그대로 두기를 권한다 — 다만 지금 무엇을 팔고 있는지는 위 표대로다.**

플래그가 사는 자리(훅의 짧은 자식)는 값이 가장 비싼 자리이고, 반대로 그 자리는 **주입 레인**이기도
하다. 즉 지금 설정은 프롬프트 지연 1.5초와 1.9GB 를 지키려고, 기억이 모델에게 닿는 유일한 통로의
hit@1 을 절반 이하로 깎고 있다. 두 판단 다 옳다 — 값이 큰 것도 사실이고 품질 손실도 사실이라,
이 교환은 어느 쪽으로 뒤집어도 한쪽을 잃는다.

뒤집는 것(플래그 제거)은 권하지 않는다. 이득은 12질의 중 4건의 순위 상승과 2건의 빈 회수
복구인데, 값은 **프롬프트마다** 1.9GB·1.5초라 비율이 안 맞는다.

둘 다 갖는 모양은 플래그가 아니라 **상주 임베더** 쪽에 있다 — 모델을 한 번 올려 두고 훅 자식이
말만 거는 구조면 1.9GB 는 한 번이고 회수는 4레인으로 돈다. 현재 코드에는 그 통로가 없다.
값싸 보이는 작은 모델은 26-07-27 실측이 한국어 음수 판별력을 적어 둔 자리라, 새 모델 대조와
`reindex` 를 먼저 치르지 않으면 회수가 조용히 무너진다.

셋 중 하나를 고르는 일이고, **아무것도 안 고르는 것(현행 유지)도 값이 명시된 선택이다.**
