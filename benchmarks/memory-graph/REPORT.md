# 기억 그래프 벤치 — 명시 링크만 vs 파생 간선까지 (26-08-06)

## 질문

1차 메모리 회수의 네 번째 RRF 스트림은 페이지의 명시 `[[링크]]` 위에서 personalized PageRank 를
돈다. 그 링크를 아무도 안 쓰면 스트림은 켜져 있어도 빈 그래프를 본다. 실제로 그랬다 —
**오딘의 개인 기억 14페이지에 명시 링크는 0개**였다. 그러면 간선을 자료에서 뽑았을 때
회수가 실제로 올라가는가, 그리고 그 대가는 무엇인가.

## 방법

`harness.py` — 합성 위키(타깃 10 + 잡음 N)를 세우고 같은 질의 집합을 두 팔에 돌린다.
시맨틱 스트림은 끈다 (`ASGARD_MEMORY_SEMANTIC=off`): 켜면 파생 간선의 몫과 임베딩의 몫이
섞여 어느 쪽이 움직였는지 못 가른다.

| 팔 | 간선 |
| --- | --- |
| `explicit` | 사람이 쓴 `[[링크]]` 만 (종전 동작) |
| `all` | + 제목 언급(`mention_links`) + 드문 낱말 공유(`term_links`) — 둘 다 결정론, 모델 없음 |

질의 두 계층:

- **direct** (n=6) — 질의 낱말이 정답 페이지에 있다. 두 팔 모두 잡아야 한다 (무회귀 대조군).
- **associative** (n=4) — 질의 낱말은 **이웃 페이지**에만 있고 정답은 그 옆이다. 그래프 확장 전용.

## 결과

그래프 모양:

| 페이지 | explicit 간선 | all 간선 | all 덩어리 |
| --- | --- | --- | --- |
| 60 | 0 | 34 | 44 |
| 300 | 0 | 1,222 | 212 |

회수 (두 규모에서 같은 수치):

| 계층 | 지표 | explicit | all |
| --- | --- | --- | --- |
| direct (n=6) | hit@1 · hit@3 · MRR | 1.000 · 1.000 · 1.000 | 1.000 · 1.000 · 1.000 |
| associative (n=4) | hit@1 | 0.750 | 0.750 |
| associative (n=4) | hit@3 | 0.750 | **1.000** |
| associative (n=4) | MRR | 0.750 | **0.875** |

지연 (1,000페이지, 질의당 벽시계, 12회):

| 팔 | p50 | 비고 |
| --- | --- | --- |
| explicit | 10.5 ms | |
| all (캐시 없음) | 42.1 ms | 매 질의마다 파생 간선을 다시 편다 |
| all (캐시 있음) | 14.2 ms | 위키 형상(`_pages_token`)이 그대로면 지난 그래프 재사용 |

## 읽는 법

`explicit` 팔의 간선이 **0개**인 것이 이 벤치의 핵심 사실이다. 종전 구현이 틀린 것이 아니라
전제가 안 맞았다 — 사람이 위키 링크를 안 쓴다. 파생 간선을 겹치자 연관 질의의 hit@3 가
0.75 → 1.00 으로 올랐고 direct 는 한 건도 안 깎였다.

캐시 없이는 1,000페이지에서 질의당 +31.6ms 다. 회수는 매 턴 도는 자리라 그 값을 매번 치를
이유가 없어, 페이지 형상이 그대로면 지난 그래프를 그대로 쓴다 (오염 판정 캐시와 같은 열쇠).
남는 값은 +3.7ms.

기본값은 `all` 이다. `ASGARD_MEMORY_GRAPH_EDGES=explicit` 또는 설정의 `memory.graph_edges` 로
되돌릴 수 있다 — 이 판정이 취향이 아니라 계측이었음을 남이 재현할 수 있어야 한다.

## 이 벤치가 못 재는 것

- **코퍼스가 합성이고 손으로 썼다.** 재는 것은 기전이 작동하는가이지 실제 위키에서 몇 점
  오르는가가 아니다. 연관 질의 n=4 는 한 건이 0.25 를 움직이는 크기라, 이 수치를 실측 개선폭으로
  읽으면 안 된다.
- **시맨틱 스트림이 꺼져 있다.** 켠 상태에서 파생 간선이 임베딩과 겹치는 몫(중복 회수)은 여기서
  안 보인다. 두 스트림이 같은 페이지를 집는다면 실제 이득은 여기보다 작다.
- **오염·모순 페이지가 없다.** 실제 위키에서는 `clean_pages` 가 걸러낸 뒤의 그래프를 본다.

## 대조 — 무엇을 가져왔고 무엇을 안 가져왔나

세 참조가 같은 한 문장을 말한다: **텍스트 조각이 아니라 부분 그래프를 회수한다.**

| 참조 | 그쪽의 방법 | Asgard 에 옮긴 것 | 안 옮긴 것과 이유 |
| --- | --- | --- | --- |
| arXiv 2603.22528 (ChatP&ID) | DEXPI 도면 → 지식 그래프 → 그래프 회수. 정확도 +18%, 토큰 −85% | 경로 회수(`path`)와 이웃 확장(`expand`) | 도면 도메인 자체. Asgard 의 정본은 도면이 아니라 페이지와 record 다 |
| microsoft/graphrag | Leiden 계층 커뮤니티 + 커뮤니티 리포트, global·local·DRIFT·basic 4모드 | 커뮤니티(`communities`) + 중심 노드(`hubs`) | Leiden 자체 — igraph 의존이 붙는다. 라벨 전파로 대체하고 상한을 `graph.py` 에 적었다. LLM 이 쓰는 커뮤니티 리포트도 안 만든다: 회수 경로에 모델을 넣으면 0-LLM 계약이 깨진다 |
| graphify | tree-sitter 결정론 추출 + 신뢰도 등급 + 하이브리드 그래프 확장, 그래프 빌드에 LLM 0원 | 결정론 간선 두 등급(`mention`=글자 그대로, `term`=드문 낱말 공유)과 SHA 기반 캐시 | 코드 AST 추출 — Asgard 는 이미 `map_graph` 가 그 자리를 진다. MCP 서버 표면도 안 만든다: `asgard memory graph --json` 이 같은 답을 준다 |

graphify 가 "임베딩이 필요 없다, 그래프 구조가 곧 유사도 신호다" 라고 말하는 자리가
`term_links` 다. 다만 그쪽은 문서·논문·이미지의 semantic 간선을 LLM 서브에이전트가 뽑고,
여기서는 안 뽑는다 — 그래서 같은 위키는 언제나 같은 그래프를 준다.
